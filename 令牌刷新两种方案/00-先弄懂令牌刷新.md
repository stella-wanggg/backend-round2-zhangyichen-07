# 先弄懂令牌刷新：从现在的代码往下走

> 这篇不写代码，只把“为什么需要刷新”“两个 token 各干什么”“流程怎么走”讲清楚。
> 看完再去看方案一、方案二，会顺很多。

## 1. 现在的登录是怎么跑的

先回忆一下现在这份代码：

```text
POST /login
  → UserServiceImpl.login 校验用户名 + 密码
  → JwtUtil.generateToken(id, name, role)
  → 返回一个字符串 token

之后每次请求
  → Header: token: eyJ...
  → Interceptor 验签名、验过期
  → 从 token 里取出 id / name / role
  → 放进 request，Controller / Service 直接用
```

这个 token 叫 **access token（访问令牌）**。

它有两个特点：

1. **它是一张“自证身份”的电子票**。服务器不存它，只验签名；签名对、没过期，就认。
2. **它有效期不长**，你现在配置的是 2 小时。

## 2. 2 小时之后怎么办

如果用户一直在用，现在的代码有“滑动续期”：token 快过期时，拦截器在响应头 `new-token` 里给一个新的，前端换掉就行。

但如果用户关掉页面两个小时，再回来：

```text
旧 token 已经过期
  → Interceptor 验 token 失败
  → 401
  → 用户只能重新输入用户名密码
```

那能不能把 access token 的有效期直接改成 30 天？

不建议，原因有三个：

1. **access token 每次请求都要带**，暴露的机会多；
2. 一旦被偷，30 天内都能用；
3. 它是无状态的，服务器没存，**想主动作废很难**。

所以才需要第二个 token。

## 3. 两个 token 的分工

用一个游乐园的比喻：

| 东西 | 好比 | 有效期 | 用在哪 |
|---|---|---|---|
| access token | 临时通行证 / 手环 | 短（15 分钟） | 每个游乐项目都要出示 |
| refresh token | 会员卡 / 身份证 | 长（7 天） | 只在“前台换手环”时出示 |

流程就是：

```text
进门登录 = 办会员卡
  → 前台给你一张会员卡（refresh token）
  → 再给你一个手环（access token）

玩项目 = 带 access token 请求业务接口
  → 手环没过期：直接玩
  → 手环快过期：保安顺手给你换个新的（滑动续期）
  → 手环已经过期：去前台，用会员卡换一个新手机

离开 = 注销会员卡（/logout）
  → 以后这张会员卡不能再换手环
```

关键点：

- **access token 不能拿去换新 token**，它只用来访问业务接口；
- **refresh token 不能用来访问业务接口**，它只能用来调 `/refresh`；
- 两张 token 不是“一长一短的同一种东西”，职责完全不同。

## 3.5 access 和 refresh 到底是什么关系

先别把它俩想成“两个 token”，想成“一张门禁卡 + 一张办卡凭证”：

- **access token = 门禁卡**：短期，每次进出业务接口都要刷；
- **refresh token = 办卡凭证**：长期，不能开门，只能去前台换新门禁卡；
- **前台 = `/refresh` 接口**；
- **前台的登记簿 = `refresh_token` 表**。

登录时，前台同时给你门禁卡和办卡凭证：

```text
登录成功
  → access token（门禁卡，短）
  → refresh token（办卡凭证，长）
```

之后的流程：

```text
进业务接口      → 只刷 access token
access 快过期   → 保安顺手换新（new-token，方案一）
access 已过期   → 拿 refresh token 去 /refresh 换新
```

具体到 HTTP：

```text
1. 登录
   POST /login
   ← { accessToken: "A1", refreshToken: "R1" }

2. 正常请求
   GET /show
   token: A1
   → 200

3. A1 过期
   GET /show
   token: A1
   → 401 + code 40101

4. 刷新
   POST /refresh
   { "refreshToken": "R1" }
   ← { accessToken: "A2", refreshToken: "R2" }

5. 重试
   GET /show
   token: A2
   → 200

6. 旧凭证不能再用
   POST /refresh
   { "refreshToken": "R1" }
   → 401（R1 已经被剪角）

7. 退出
   POST /logout
   { "refreshToken": "R2" }
   → R2 作废；A2 在过期前仍然能刷
```

所以它们的关系是：

| | access token | refresh token |
|---|---|---|
| 是什么 | 门禁卡 | 办卡凭证 |
| 用途 | 访问业务接口 | 只用来换新门禁卡 |
| 有效期 | 短 | 长 |
| 服务端怎么认 | 验签名 | 查数据库里的哈希 |
| 存哪 | 只在客户端 | 客户端 + 数据库（只存哈希） |
| 能否撤销 | 不能 | 能 |
| 谁产生 | 登录 / 刷新 | 登录 / 刷新（轮换） |

两句话记住：

1. **refresh 不是把 access 变长，而是发一张新的 access；旧的 access 在过期前仍然有效。**
2. **它们不是新旧关系，也不是父子关系，而是同一用户的两种证件：一个高频使用，一个低频换证。**

为什么不能只留一个长期 access？因为 access 每个请求都带，暴露多，又不能撤销；refresh 很少发送，存在服务端，可以撤销、可以轮换。分工不同，风险才控得住。

## 4. 一条时间线，把两种机制串起来

假设 access token 15 分钟，refresh token 7 天，滑动续期阈值 5 分钟：

| 时间 | 动作 | access token 状态 | refresh token 状态 | 结果 |
|---|---|---|---|---|
| 10:00 | 登录 | 新签发，15 分钟 | 新签发，7 天 | 200，拿到两个 token |
| 10:09 | 请求 | 还剩 6 分钟 | 有效 | 200，正常放行 |
| 10:11 | 请求 | 还剩 4 分钟 | 有效 | 200 + 响应头 `new-token` |
| 10:12 | 用新 token 请求 | 新签发 | 有效 | 200 |
| 10:30 | 用旧的 access 请求 | 已过期 | 有效 | 401 + code `40101` |
| 10:30 | 调 `/refresh` | — | 有效 | 200，换到新 access + 新 refresh |
| 10:31 | 重试原请求 | 新签发 | 新签发 | 200 |
| 第 8 天 | 调 `/refresh` | — | 过期 | 401，回登录页 |

这里有两件事同时发生：

- **滑动续期**：token 还没过期，只是快到期，拦截器主动换；
- **刷新**：token 已经过期，前端拿 refresh token 去换。

所以方案一和方案二不是二选一，而是**一个管“快过期”，一个管“已过期”**。

## 5. 为什么 refresh token 要存数据库

access token 不需要存数据库，因为它是自证的：签名对、没过期就认。

refresh token 不一样，它需要满足三件事：

1. **能撤销**：用户退出登录后，这张卡要立刻作废；
2. **能轮换**：用过一次就换新的，旧的作废；
3. **能查状态**：这张卡是不是被撤销了、是不是过期了。

这些都需要服务器“记住”它，所以要有 `refresh_token` 表。

### 为什么只存哈希

客户端拿到的是 refresh token 原文，数据库里存的是它的 SHA-256：

```text
客户端：Xy7k...（原文）
数据库：9f2c...（64 位十六进制哈希）
```

这样即使数据库泄露，攻击者拿到的也只是哈希，不能直接当 refresh token 用。

### 什么是轮换（rotation）

每次调用 `/refresh`：

```text
旧 refresh token → 标记 revoked = 1
                → 生成一个新的 refresh token
```

就像换新会员卡时把旧卡剪角。旧卡即使被别人捡到，也用不了。

### 为什么不用 JWT 做 refresh token

技术上可以，但 JWT 是无状态的，想撤销就得再加黑名单；用“随机字符串 + 数据库”反而更直接：

- 随机字符串没有信息，不怕被解析；
- 数据库一行记录就能撤销；
- 轮换、过期、设备管理都好做。

## 6. 为什么不能把两个 token 合并成一个

因为它们的“暴露面”和“生命周期”不一样：

| | access token | refresh token |
|---|---|---|
| 发送频率 | 每个请求都发 | 只在刷新时发 |
| 有效期 | 短（15 分钟） | 长（7 天） |
| 是否存库 | 不存 | 存哈希 |
| 是否能撤销 | 很难 | 容易 |
| 被偷后的影响 | 15 分钟内可用 | 直到被撤销/过期 |

如果只用一个长期 token：

- 每次请求都带着它，被偷的概率更高；
- 被偷后很长时间都能用；
- 想撤销又因为无状态而很麻烦。

拆成两个，就是**把“高频使用”和“长期保存”分开**。

## 7. 刷新到底“刷”了什么

一句话：

> 用长期保存的 refresh token，换一对新的 access token + refresh token。

注意是**一对**，不是只换 access：

- 新 access token：继续访问业务接口；
- 新 refresh token：旧的同时作废，防止旧卡被重复使用。

## 8. 免登录是什么意思

“免登录”不是永远不用登录，而是：

```text
用户关掉页面 → 过几天再打开
  → 本地还有 refresh token
  → 前端自动调 /refresh
  → 成功：直接进首页，不用输密码
  → 失败（过期/撤销）：回登录页
```

所以免登录的边界是 refresh token 的有效期（比如 7 天），不是无限期。

## 9. 术语表

| 术语 | 大白话 |
|---|---|
| access token | 短命通行证，访问业务接口用 |
| refresh token | 长命会员卡，只用来换新通行证 |
| 滑动续期 | 通行证快到期但还没到期，保安顺手换新 |
| 刷新（refresh） | 通行证已经过期，拿会员卡去前台换新 |
| 轮换（rotation） | 换新卡时旧卡剪角作废 |
| 撤销（revoke） | 主动让某张会员卡失效（退出登录） |
| 哈希（hash） | 数据库只存卡号的指纹，不存卡本身 |
| `40101` | 自定义业务码：access token 过期了，去刷新 |
| single-flight | 多个请求同时要刷新时，只发一次刷新请求，其他等结果 |
| 免登录 | 用 refresh token 自动换新，不用重新输密码 |

## 10. 几个常见误区

**误区 1：refresh token 是有效期更长的 JWT。**
不一定。更常见的做法是随机字符串，存数据库；它不需要包含用户信息。

**误区 2：refresh token 也能访问业务接口。**
不能。它只应该发给 `/refresh`，业务接口只认 access token。

**误区 3：退出登录后 access token 立刻失效。**
不会。access token 是无状态的，在过期前仍然有效；退出只能撤销 refresh token，阻止后续续期。

**误区 4：一个用户只有一个 refresh token。**
每次登录都可以生成一个；多设备登录就是多条记录，可以分别撤销。

**误区 5：刷新就是重新登录。**
刷新不需要用户名密码，只需要 refresh token；只有 refresh token 也失效了才回登录页。

**误区 6：把 access token 有效期设成 30 天就不用刷新了。**
这样更不安全，而且解决不了“主动撤销”的问题。

后面两份方案里，可以带着这些问题去读：

| 问题 | 去哪里找答案 |
|---|---|
| access token 在哪生成 | `JwtUtil.generateToken` |
| access token 在哪校验 | `Interceptor.preHandle` |
| 快过期怎么换新 | `tokenNearExpiration` + 响应头 `new-token`（方案一） |
| refresh token 在哪生成 | `RefreshTokenService.create`（方案二） |
| refresh token 存哪 | `refresh_token` 表 + `RefreshTokenMapper` |
| 怎么换新 | `/refresh` + `verify` + `rotate`（方案二） |
| 退出怎么作废 | `/logout` + `revoke`（方案二） |
| 为什么 `/refresh` 不被拦截 | `WebConfig.excludePathPatterns` |
| 为什么刷新不能直接查用户 | 用 `getUserByIdForRefresh`，不要用带权限判断的 `getUserById` |

## 12. 离线、过期和 refresh 兜底

先给结论：

> **会兜底，但不是服务器在用户离线时自动续，而是用户回来时，前端拿 refresh token 去换新的 access token。**

滑动续期只会在“有请求、且 access 快过期”时发生。人不在线就没有请求，所以拿不到滑动续期是正常的——refresh token 就是专门给这种情况兜底的。

### 12.1 能不能兜住，看三个前提

1. **refresh token 还没过期**（方案二里是 7 天）；
2. **refresh token 没被撤销**（没退出登录、没被轮换掉）；
3. **前端把 refresh token 存住了，并且实现了刷新逻辑**：
   - 启动时主动调 `/refresh`，或
   - 收到 `401 + 40101` 时调 `/refresh`，成功后再重试原请求。

如果前端只把 token 放在内存里，关掉页面就没了，refresh 也帮不上；要放在 `localStorage` 这类能持久保存的地方（作业里够用）。

### 12.2 用时间线看

假设 access 15 分钟，refresh 7 天：

| 情况 | access | refresh | 结果 |
|---|---|---|---|
| 离线 10 分钟 | 已过期 | 有效 | 回来调 `/refresh`，成功 |
| 离线 3 天 | 已过期 | 有效 | 回来调 `/refresh`，成功 |
| 离线 6 天 | 已过期 | 还剩 1 天 | 成功；刷新后 refresh 重新变 7 天 |
| 离线 8 天 | 已过期 | 已过期 | 兜不住，重新登录 |
| 主动退出登录 | 可能还没过期 | 已撤销 | 兜不住，重新登录 |

注意最后一条：**退出登录后，access token 在它自己过期前可能还能用，但 refresh token 已经被撤销，不能再换新的了。** 这就是为什么 access 要短。

### 12.3 为什么 refresh 能兜住

因为 refresh token 的有效期和 access 是**两条独立的时钟**：

- access：登录/刷新时发，15 分钟后过期；
- refresh：登录/刷新时发，7 天后过期；
- access 过期不会让 refresh 一起过期；
- 只要 refresh 还在有效期内，就能换一对新的 access + refresh。

而且方案二每次刷新都会生成**新的 refresh**，有效期重新算 7 天。所以用户只要每 7 天内打开一次，理论上可以一直免登录；超过 7 天没打开，才需要重新登录。

### 12.4 兜不住的情况

- refresh 超过 7 天；
- 用户点了退出登录，refresh 被 `revoked=1`；
- 这个 refresh 已经被轮换过，旧的那张不能再用；
- 浏览器清空了 localStorage；
- 前端没写“收到 40101 去刷新”的逻辑；
- 数据库里的 `refresh_token` 记录被删了。

### 12.5 对应到现在的代码

- 现在还没有 `/refresh`，所以目前 access 过期就是重新登录，refresh 兜不了底；
- 按方案二加上 `/refresh`、`refresh_token` 表、`WebConfig` 放行 `/refresh`、拦截器返回 `40101` 之后，才会真正兜底；
- 前端还要配合：收到 `40101` → 调 `/refresh` → 拿新 access 重试。服务器不会替前端发这个请求。

一句话：

> **refresh 不是“自动续期”，而是“回来时可以换新的”。离线期间它只是在倒计时；只要 7 天内回来，就能用；超过 7 天，才重新登录。**

## 13. 一句话总结

```text
access token：常用、短命、无状态
refresh token：少用、长命、有状态、可撤销

滑动续期：快过期时换
refresh：已过期时换

两个一起用：
  活跃用户无感续期
  久未访问也能免登录（直到 refresh 过期）

离线期间：
  滑动续期不会发生
  回来时用 refresh 换新
  refresh 过期 / 被撤销 / 丢失 → 重新登录
```
